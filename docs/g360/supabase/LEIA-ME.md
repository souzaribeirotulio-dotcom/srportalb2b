# Ponte de acesso no Supabase

A Edge Function recebe duas ações do navegador. Em `pedir_link`, ela pede o link à API dos sistemas externos e envia um e-mail. Em `abrir_sessao`, ela confere o token do comprador em `GET me` e devolve uma sessão do Supabase. As chamadas de catálogo, revisão e pedidos continuam diretas do navegador para a API.

O exemplo fixa `@supabase/supabase-js` em **2.119.0**. Para emitir a sessão após o login externo, usa `auth.admin.createUser` para provisionar a identidade, `auth.admin.generateLink` para gerar um comprovante de uso único e `auth.verifyOtp` para consumi-lo na função. O comprovante fica no servidor e o Supabase não envia e-mail nesse fluxo. O UUID e o endereço técnico reservado em `example.invalid` derivam do par loja e código do comprador. Isso evita vincular compras pelo e-mail do cadastro, que pode ser compartilhado ou substituído na homologação. O identificador fica em `app_metadata`, gravado pelo servidor. [Versão 2.119.0](https://github.com/supabase/supabase-js/releases/tag/v2.119.0) · [Criar usuário](https://supabase.com/docs/reference/javascript/auth-admin-createuser) · [Gerar comprovante](https://supabase.com/docs/reference/javascript/auth-admin-generatelink) · [Verificar comprovante](https://supabase.com/docs/reference/javascript/auth-verifyotp)

## Preparar a função

1. Use `supabase functions new ponte-g360` no projeto de vocês. Copie [index.ts](index.ts) e [ponte.ts](ponte.ts) para `supabase/functions/ponte-g360/`.
2. Aplique [minha-lista.sql](minha-lista.sql) como migração no projeto de vocês. A regra de acesso exige uma sessão vinculada, a loja e o código do comprador. Guarde o `id` numérico da API em `produto_id` para carrinho, pedido e filtro `produto_ids` do histórico. Para carregar os produtos da lista, envie esses identificadores no filtro `ids` do catálogo. O exemplo guarda apenas `produto_id`. A API devolve o código comercial no catálogo quando a tela precisar exibi-lo. Use o mesmo recorte nas demais tabelas de acesso do comprador e revise as políticas existentes. Mantenha o esquema `g360_ponte_privado` fora dos esquemas expostos pela API de dados. [RLS no Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)
3. Preencha as variáveis do [.env.exemplo](.env.exemplo) nos segredos da Edge Function. Use uma configuração por loja e ambiente. `G360_BASE_URL` é a URL-base da instalação, sem o caminho da operação. `PORTAL_ORIGENS` é uma lista de origens exatas separadas por vírgulas. `PORTAL_PAGINA_SENHA` precisa pertencer a uma delas. O runtime hospedado fornece `SUPABASE_URL` e a chave secreta `default` de `SUPABASE_SECRET_KEYS`. Ative **IP Address Forwarding** em **Authentication > Rate Limits**. O Auth só aceita o IP repassado com a chave secreta moderna, de prefixo `sb_secret_`. A chave legada `service_role` não aceita esse repasse. O SDK mantém a chave secreta no servidor. Use um segredo aleatório exclusivo de pelo menos 32 bytes em `G360_OCORRENCIAS_HMAC` e mantenha-o estável para deduplicar ocorrências ao longo do dia. [Variáveis de ambiente](https://supabase.com/docs/guides/functions/secrets) · [Repasse de IP no Auth](https://supabase.com/docs/guides/auth/rate-limits#ip-address-forwarding)
4. Adapte `enviarEmail` ao provedor escolhido por vocês. O destinatário é exclusivamente `dados.email`. Use o fragmento `#token=…` montado pela função. Desative rastreamento de cliques ou reescrita de URL nesse e-mail. Na página de senha, leia o fragmento com `URLSearchParams` e limpe-o com `history.replaceState` antes de carregar scripts de análise. Envie o token e a senha nova a `POST acessos/senha`.
5. Configure Auth com confirmação de e-mail e confirmação de troca de e-mail nos dois endereços. Reserve as contas técnicas para esta função e exclua o sufixo técnico de fluxos públicos de e-mail, cadastro e vinculação de provedores. Desative cadastro aberto e vinculação manual se o projeto não precisar deles. Controle a emissão de links também na borda do projeto, com limite por endereço e proteção contra automação. Uma origem permitida viabiliza o navegador e pode ser reproduzida por um cliente HTTP. [Configuração do Auth](https://supabase.com/docs/guides/auth/general-configuration)
6. Em `supabase/config.toml`, configure a verificação somente para esta função. As duas chamadas chegam antes de o comprador ter um JWT do Supabase. A segunda ação verifica o Bearer da API pelo `GET me`. [Configuração de funções](https://supabase.com/docs/guides/functions/function-configuration)

   ```toml
   [functions.ponte-g360]
   verify_jwt = false
   ```

7. Rode os testes simulados abaixo. Para ensaiar o repasse real, use `supabase functions deploy ponte-g360` no projeto hospedado de teste, com os segredos injetados pelo runtime. Confirme que o ingresso fornece o cabeçalho e que o Auth contabiliza por IP do comprador. `supabase functions serve` usa a pilha local e serve para simular o ingresso, sem validar o repasse no serviço hospedado.

Na hospedagem gerenciada, a função lê o IP de `CF-Connecting-IP`, preenchido no ingresso, e envia um único IPv4 ou IPv6 como `sb-forwarded-for` na verificação. A abertura falha se o IP estiver ausente ou inválido. Se usarem um ingresso próprio, garantam que ele sobrescreva o cabeçalho com o IP observado e que a função só aceite tráfego desse ingresso. [Cabeçalhos do ingresso do Supabase](https://supabase.com/docs/guides/observability/log-field-reference#captured-http-headers) · [IP preenchido pela plataforma](https://supabase.com/docs/guides/api/query-plans)

## Chamar do navegador

Chame `POST` na URL configurada da função, com `Content-Type: application/json`. Use `fetch` com esse cabeçalho. A função aceita somente as origens configuradas, com esse cabeçalho no preflight.

- Primeiro acesso ou recuperação. Envie `{"acao":"pedir_link","documento":"12.ABC.345/01DE-35"}`. Mostre a mensagem do HTTP 202. A consulta e o envio são tarefas de fundo para que a resposta pública seja igual em caso de emissão ou recusa do cadastro. A mensagem confirma o recebimento da solicitação. O provedor precisa entregar o e-mail. [Tarefas de fundo](https://supabase.com/docs/guides/functions/background-tasks)
- Depois de `POST sessoes` na API, envie `{"acao":"abrir_sessao","token":"<preencha>"}`. No HTTP 200, passe somente `sessao` a `supabase.auth.setSession(sessao)`. Use `api_expira_em` e `api_inatividade_minutos` para controlar o acesso na interface. O campo `api_vinculo_expira_em` informa até quando a regra de acesso aceita essa sessão para os dados privados. Guarde o token no `sessionStorage` da aba quando `continuar_conectado` efetivo for false; somente com true, no `localStorage`, com chave própria por loja/comprador. A caixa vem desmarcada, só aparece com dias > 0 e mostra o aviso de computador compartilhado. Sair e 401 apagam ambos, como dizem as instruções (seção 5). Depois de recarregar a página, confira a sessão com `GET me` e chame `abrir_sessao` de novo com esse token. Um 401 pede novo login. Em 503, ofereça tentar de novo enquanto a sessão da API estiver válida. [Instalar a sessão](https://supabase.com/docs/reference/javascript/auth-setsession)

## Manter as sessões alinhadas

- A sessão da API decide se o comprador continua autenticado. Na sessão normal, controle a inatividade indicada pela API desde a última chamada aceita. Na longa, ignore esse limite em minutos: reconfira GET me sob demanda, com uso a cada N dias e teto absoluto de 90 dias desde o login. O prazo curto do vínculo do Supabase continua separado da validade do token da API. Ao retomar uma aba, confira a sessão da API quando o estado estiver incerto. Se já for preciso abrir outro vínculo, a própria função fará a conferência. Evite consultas periódicas que mantenham artificialmente o comprador ativo. Ao expirar ou receber 401, bloqueie a interface privada, limpe o token da API e encerre a sessão do Supabase com `signOut({ scope: "local" })`. Trate falhas de comunicação sem liberar a tela privada.
- Ao sair, chame `DELETE sessao` na API e encerre a sessão local do Supabase. Quando `PUT senha` devolver o token substituto, revogue as sessões Supabase daquele comprador com `signOut({ scope: "global" })` antes de abrir a nova sessão pelo token substituto. Após a recuperação, as sessões anteriores da API são revogadas. As abas que tinham sessão anterior devem encerrá-la quando a API recusar o token antigo. Se houver uma sessão Supabase anterior do mesmo comprador disponível no navegador que concluiu a recuperação, encerre-a também antes do novo login.
- Para os dados privados, a regra SQL aceita a sessão até o primeiro destes prazos após a conferência: `G360_RECONFERENCIA_MINUTOS`, a inatividade configurada na loja ou a expiração absoluta da API. O padrão de 5 minutos limita a janela residual de acesso após revogação, sem exigir conferência a cada leitura. Quando esse intervalo terminar, encerre a sessão local anterior e abra outra com `abrir_sessao` ao voltar a uma tela de dados privados. A função confere a API antes de conceder outro intervalo. A remoção da sessão do Supabase também corta esse acesso. A API pode revogar o acesso antes do fim do intervalo, inclusive em caso de bloqueio no G360 ou troca de senha. A conferência no navegador faz a interface reagir a isso. Para garantir revogação imediata também contra chamadas diretas à API de dados do Supabase, faça as operações que exigem essa garantia por um serviço que confira `GET me` a cada operação e retire o acesso direto a essas tabelas. Reserve esse serviço para dados do Supabase. Catálogo e pedidos continuam diretos à API dos sistemas externos. [Sessões do Supabase](https://supabase.com/docs/guides/auth/sessions) · [Encerrar sessão](https://supabase.com/docs/reference/javascript/auth-signout)

## Capacidade de login e reconferência

A seção 3 do escopo prevê um `GET me` pela função no login. Reconferir para renovar o vínculo dos dados privados é uma escolha deste exemplo. Cada renovação volta a chamar `GET me` e reabre a sessão no Auth. Faça isso sob demanda, quando o comprador voltar a usar dados privados e o vínculo tiver expirado. Um intervalo menor reduz a janela residual após bloqueio e aumenta as chamadas. Um intervalo maior reduz as chamadas até o limite de inatividade da loja e amplia a janela. Ajuste o inteiro positivo em `G360_RECONFERENCIA_MINUTOS`.

- **Supabase Auth.** O limite padrão de `/auth/v1/verify` é de 30 verificações a cada 5 minutos por IP, com rajadas de até 30. Com o repasse habilitado, é o IP do comprador que conta. Pessoas na mesma rede podem dividir esse limite. Se 30 compradores no mesmo IP renovarem a cada 5 minutos, já consomem a média disponível antes de contar novos logins. Se precisarem aumentar a capacidade, ajustem **Verification requests** em **Authentication > Rate Limits** e tratem o 429 sem reenvios em sequência. [Limites do Auth](https://supabase.com/docs/guides/auth/rate-limits)
- **API do G360.** Cada `GET me` da função conta nas 240 chamadas por minuto por IP de saída e loja. Some os logins por minuto, as outras chamadas da função e, para estimar o fluxo sustentado, divida o número de compradores que renovam pela janela efetiva em minutos. Por exemplo, 500 compradores renovando a cada 5 minutos geram em média 100 chamadas por minuto ao G360, além dos logins e demais chamadas no mesmo IP. Reserve margem para rajadas e janelas menores. Catálogo, fotos, checkout e pedidos continuam diretos do navegador.

## Mostrar ocorrências no painel

Para `responsavel: fornecedor`, registre a ocorrência com `loja`, `comprador_codigo` quando disponível, `codigo`, `request_id` e `operacao`, por exemplo `POST pedidos`. O banco preenche `registrada_em`. Se o envio devolver `erro.campos.pendencias`, faça o registro pela categoria de cada pendência. Use o método e o caminho da operação sem parâmetros de consulta nem valores de rota.

A sessão do comprador só insere ocorrências da própria loja e do próprio comprador. Na chamada ao Supabase, use `insert` sem pedir retorno com `.select()`. As linhas informadas pelo navegador servem para triagem. Use o `request_id` para conferir a origem no suporte.

Para ler no painel, um administrador do Supabase deve preencher `app_metadata.g360_painel_loja` com o slug da loja em uma conta própria da equipe do painel, pelo SQL Editor ou pelo servidor autorizado. Essa conta não identifica o operador. Permissões por operador passam pela função, que confere quem está logado com `GET operadores/me` (seção "Quem está logado e o que pode fazer" do guia). A sessão de comprador emitida pela ponte carrega apenas a identidade de comprador. As credenciais administrativas do Supabase ficam no servidor.

Na emissão de link, a função grava pelo servidor apenas erros com `responsavel: fornecedor`, mantendo a resposta neutra. A operação é registrada sem código do comprador, pois a recusa não o devolve. Um marcador calculado com segredo limita o registro a um por documento e loja por dia UTC, inclusive com chamadas simultâneas. O marcador fica em tabela privada, fora do painel. O documento original, a senha, a mensagem, o corpo da requisição e os tokens ficam fora dos registros. A rotina de retenção do projeto pode excluir marcadores antigos após o dia UTC correspondente.

## Conferir a integração

```powershell
deno check --no-lock index.ts ponte_test.ts
deno lint index.ts ponte.ts ponte_test.ts
deno test --no-lock ponte_test.ts
```

Os testes usam respostas simuladas. Na homologação de vocês, confira o e-mail de teste da loja, duas sessões com IPs diferentes, a separação dos registros da Minha Lista e a saída depois de expiração, bloqueio e troca de senha.
