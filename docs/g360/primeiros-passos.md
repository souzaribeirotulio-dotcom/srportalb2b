# Primeiros passos

Este guia acompanha a documentação da **API dos sistemas externos**. A seção 3 do escopo descreve a divisão de trabalho. O G360 decide quem pode entrar e comprar e é a fonte de cliente, produto, preço, estoque e pedido. Bloquear um usuário no Supabase não bloqueia a compra pela API. O Supabase de vocês guarda referências, como o código do cliente e o identificador do produto, e o que nasce no portal, como Minha Lista, negociações, feriados e envio de e-mails. Consultem preço, estoque e situação do pedido na API no momento do uso.

## Quem pode integrar

Esta documentação é aberta, mas a integração não é. Só integra a empresa liberada pela Movimento Sistemas. Sem a liberação, a API fica desligada no G360. Em cada chamada, o servidor confere se a API está liberada para a loja. Nas operações protegidas, ele confere também a sessão e as permissões do comprador ou do operador no G360. Na liberação, a Movimento entrega a chave de sistema da loja, por um canal separado. Ela fica só no servidor de vocês e serve para pedir o link de acesso. As operações sensíveis ficam registradas para auditoria. Para pedir a liberação, fale com a Movimento Sistemas.

## O que cada equipe prepara

A Movimento informa a URL-base, o slug da loja e os usuários de teste. A chave de sistema e as senhas são entregues por um canal separado. Usem a URL-base seguida de `/b2b/v1/lojas/{loja}`. O slug tem 16 caracteres hexadecimais minúsculos.

Informem as origens exatas do portal em produção, homologação e desenvolvimento local. A origem é esquema, host e porta, quando a porta é diferente da padrão. Por exemplo, `https://portal.example.invalid`. Use o host em minúsculas e omita a porta padrão do HTTPS. Em HTTP, só se aceita `localhost` com porta explícita diferente de 80, como `http://localhost:5173`. A lista aceita origens fixas, conforme o item 35.

## Quem chama a API

```text
Navegador → API do G360
  Login, catálogo, checkout e pedidos

Navegador → Função do Supabase → API do G360
  Primeiro acesso / recuperação → POST acessos/links
  Ponte no login → GET me com o token do comprador

Função do Supabase → Provedor de e-mail
  Link para o endereço devolvido pela API

Função do Supabase → Supabase Auth → Navegador
  Sessão do Supabase para o comprador conferido
```

O navegador chama a API direto. Nas operações autenticadas, envie `Authorization: Bearer <token>` da sessão do comprador. Usar um servidor intermediário para todas as chamadas faria os compradores dividirem o mesmo limite de 240 chamadas por minuto por endereço e loja. Redes que já compartilham um endereço externo também dividem esse limite.

A função do Supabase guarda a `X-Chave-Sistema` no servidor, pede o link, envia o e-mail e, no login, confere o token da API para abrir a sessão do Supabase. O envio de e-mail é da equipe de vocês.

## Primeiro acesso e recuperação

1. Envie o documento digitado pelo comprador à função do Supabase.
2. A função chama `POST acessos/links` com `X-Chave-Sistema`, sem o cabeçalho `Origin`. Emita o link apenas em resposta a uma solicitação do comprador.
3. Se a API retornar 201, envie o e-mail somente para `dados.email`. Em homologação, uma emissão bem-sucedida devolve o e-mail de teste da loja. A emissão ainda exige um e-mail válido no cadastro.
4. Devolva a mesma mensagem ao navegador para emissão ou recusa de cadastro. Por exemplo, “Se a solicitação puder ser atendida, você receberá as instruções por e-mail.”
5. Coloque o token no fragmento do link, após `#`, para ele ficar fora das requisições HTTP e do `Referer`. A página lê e remove o fragmento do endereço e envia `token` e `senha_nova` para `POST acessos/senha`. Evite registrar o fragmento ou o corpo da chamada.
6. Depois do 204, faça o login em `POST sessoes` com a senha nova.

O link vale 30 minutos e só pode ser usado uma vez. Uma emissão nova invalida o link anterior. A gravação da senha pelo link encerra as sessões já abertas.

## Login e sessão do Supabase

O navegador chama `POST sessoes` e envia o token retornado à função. A função chama `GET me` com o Bearer da API e vincula a conta do Supabase à loja e a `dados.comprador.codigo`. O escopo prevê essa conferência uma vez, no login. O exemplo da ponte permite reconferir sob demanda para limitar a exposição dos dados privados. Cada nova abertura conta como mais um `GET me` no IP da função e mais uma verificação no Supabase Auth. A sessão da API expira por inatividade, 8 minutos por padrão e configurável, ou pelo limite absoluto de 12 horas indicado em `expira_em`.

A sessão da API manda. Em 401 numa operação com sessão do comprador, encerre também a sessão do Supabase e limpe os dados locais. Em `PUT senha`, troque o token pelo novo, encerre a sessão anterior do Supabase e refaça a ponte. O bloqueio de acesso no G360 invalida a sessão da API nas bases que aplicam o item 03. A situação comercial também pode bloquear o envio de pedidos com a sessão ainda válida. Confira a situação em `GET me`. Use regras de acesso por cliente no Supabase e exija sessão válida para acessar os dados privados. O exemplo documenta a janela configurável e os limites que uma nova conferência consome. A API e o Supabase não propagam revogações automaticamente entre si.

## Ordem das chamadas para comprar

1. `GET loja` apresenta a loja e informa o limite de inatividade.
2. `POST sessoes` abre a sessão e `GET me` identifica o comprador e a situação de compra.
3. `GET produtos` ou `POST produtos/busca` consulta o catálogo. Use `GET grupos`, `GET marcas` e `GET produtos/{id}/fotos/{item}` para filtros e fotos. Para a Minha Lista e a recompra, obtenha os identificadores no Supabase ou pelos `produto_id` de `GET historico-compras`. Passe-os ao filtro `GET produtos?ids=101,102` ou envie `{"ids":[101,102]}` a `POST produtos/busca` para listas longas. Quando `fotos[]` tiver itens, a primeira foto é a capa e `imagem` é o caminho relativo ao prefixo da loja, por exemplo `produtos/101/fotos/1`. Baixe a foto com o Bearer do comprador e use os bytes retornados para exibição. Com a lista vazia, `imagem` pode conter o nome legado. A API aceita até 500 identificadores por filtro e devolve preço, disponibilidade e referências de fotos dos produtos visíveis ao comprador. Use `pagina` e `limite` para percorrer mais de 50 resultados visíveis.
4. `GET opcoes` lista endereços e pagamento. Para inclusão, consulte `GET enderecos/referencias` e chame `POST enderecos`.
5. `POST revisoes` recalcula o carrinho. Mesmo no HTTP 200, confira `dados.pode_enviar` e mostre `dados.pendencias`. Se houver bloqueio, resolva as pendências e revise de novo. A previsão de entrega, quando exigida, vem do portal. A API aceita a data no formato AAAA-MM-DD.
6. `POST pedidos` recebe o carrinho revisado, a `assinatura` mais recente e a `Idempotency-Key`. O primeiro envio bem-sucedido retorna 201. O pedido pode já sair numerado ou aguardar aprovação no G360.
7. `GET pedidos/por-chave/{chave}` recupera um resultado incerto. `GET pedidos` lista pedidos feitos pela API e `GET pedidos/{id}` mostra o detalhe.
8. `DELETE sessao` encerra a sessão da API. Encerre também a do Supabase.

### Referências de produto na Minha Lista

Na coluna `produto_id`, guarde o `id` numérico do catálogo. É o mesmo identificador usado em `produto_id` na revisão e no pedido e em `produto_ids` no filtro do histórico de compras. O filtro `ids` aceita esse mesmo identificador. O código comercial `codigo`, como `P-101`, continua disponível para busca por `codigos`.

## Como reenviar um pedido

Gere uma chave por tentativa de envio intencional. Use 16 a 64 caracteres, com letras, números, `_` e `-`. Guarde a chave e o corpo até obter uma resposta final. A chave pertence ao comprador na base da loja e continua válida depois de um novo login.

| Resultado | O que fazer |
|---|---|
| Timeout, conexão caída ou resposta incerta | Consulte `GET pedidos/por-chave/{chave}`. Depois do timeout, 404 `NAO_ENCONTRADO` na consulta por chave é esperado, embora venha com `responsavel: integracao`. O pedido não foi gravado. Reenvie o mesmo corpo com a mesma chave. |
| 409 `OPERACAO_EM_ANDAMENTO` | A API encontrou uma operação concorrente. Outro envio da mesma chave pode estar em processamento. Aguarde pelo menos 3 segundos e reenvie com a mesma chave. |
| 409 `VENDA_EM_ANDAMENTO` | O envio recusado não gravou pedido. O saldo de um produto do carrinho está reservado por uma venda do fornecedor em andamento e o que sobra não cobre o pedido, ou essa venda está gravando a reserva naquele instante. Com saldo para os dois, o pedido passa. Aguarde pelo menos 3 segundos e reenvie o mesmo corpo com a mesma chave. Se uma tentativa anterior já confirmou o mesmo carrinho, o reenvio retorna 200 com o pedido existente. |
| 409 `REVISAO_ALTERADA` | Revise de novo, mostre o resultado atualizado ao comprador e use a nova assinatura com a mesma chave para concluir a tentativa. Essa recusa não compromete a chave. |
| 409 `CHAVE_REUTILIZADA` | Já existe um pedido associado a essa chave, mas o envio não é comparável ou o carrinho normalizado é diferente. Consulte pela chave antes de fazer qualquer novo pedido. |
| 503 `INDISPONIVEL` | Aguarde pelo menos 30 segundos. Para envio, consulte o resultado pela mesma chave e mantenha a chave no reenvio. |
| 201 ou 200 com pedido | Registre o pedido retornado. O 200 de repetição recupera o pedido existente e dispensa uma nova assinatura. |

Gere outra chave quando o comprador decidir começar um novo pedido, depois de resolver o resultado da tentativa anterior. Corrigir uma revisão recusada durante a mesma tentativa não exige uma chave nova.

## Respostas e erros

Sucesso JSON traz `dados` e `request_id`. Listagens paginadas incluem `paginacao` quando prevista na operação. Foto bem-sucedida é binária e HTTP 204 tem corpo vazio. O envelope de erro tem `erro.codigo`, `erro.mensagem`, `erro.responsavel`, `erro.campos` e `request_id`. O objeto `erro.campos` pode vir vazio. Métodos e parâmetros de rota inválidos podem ser recusados antes do envelope da API.

Mostre `erro.mensagem` e `pendencias[].mensagem` como vieram. Use `responsavel` para decidir como orientar a pessoa na tela. Use `codigo` para os fluxos específicos, como reenvio do pedido e emissão do link. Guarde o `request_id` para o suporte. Quando `responsavel` faltar ou tiver valor desconhecido, aplique o tratamento de `integracao`.

- `usuario`: peça a quem está na tela, comprador ou operador, para corrigir a entrada ou escolher outra opção.
- `fornecedor`: mostre a mensagem. Registre no Supabase o código, a loja, o `request_id`, a operação, a data e hora e o código do comprador quando disponível. O painel usa o registro para encaminhar ajustes no G360. Guarde esses campos sem incluir a mensagem, o corpo da requisição, o documento, a senha ou o token.
- `tentar_de_novo`: informe a espera e dê opção de tentar novamente. No envio de pedido, siga a matriz de reenvio.
- `integracao`: mostre uma mensagem genérica com o `request_id` e registre o identificador para investigação. A consulta por chave após timeout tem o tratamento descrito na matriz.

Em `REVISAO_BLOQUEADA`, use cada item de `erro.campos.pendencias` com seu próprio `responsavel`. Isso também vale para as pendências retornadas na revisão. `ESTOQUE_SEM_CONFIGURACAO` é um erro de fornecedor que pode aparecer se a configuração mudar entre a revisão do envio e a conclusão. Em geral, a revisão já identifica a indisponibilidade com `PRODUTO_INDISPONIVEL` ou `ITEM_BLOQUEADO`.

Em `POST acessos/links`, a função do Supabase sempre devolve a mensagem neutra ao navegador. Quando a API responder com `responsavel: fornecedor`, a função registra a ocorrência no servidor, com limite por documento e dia. Documento inválido ou cadastro não localizado fica fora da fila do painel.

## Limites e CORS

| Limite | Regra |
|---|---|
| Chamadas | 240 por minuto por endereço IP e loja, incluindo fotos. Slugs desconhecidos compartilham 60 por minuto por IP. |
| Login do comprador | Em 15 minutos, 5 falhas por documento e IP, 40 por IP e 50 por documento, por loja. O sucesso zera somente o contador do par documento e IP. |
| Login do operador | Contadores próprios em 15 minutos, por loja. São 5 falhas por usuário e IP, 40 por IP e 50 por usuário. |
| Link | Em 15 minutos, 3 emissões por documento na loja, 60 por chave de sistema e 10 tentativas de gravar senha por IP. |
| Corpo e paginação | Até 65.536 bytes. O POST de foto do operador aceita até 2.804.096 bytes de corpo, com um JPEG de até 2 MiB. Para produtos e pedidos, `pagina` de 1 a 100.000 e `limite` de 1 a 50. Padrões 1 e 20. |
| Carrinho | De 1 a 100 linhas e até 400 caracteres na observação. |

Só origens exatas cadastradas na loja recebem CORS. Curingas e domínios de pré-visualização ficam fora da lista. O preflight aceita `Authorization`, `Content-Type` e `Idempotency-Key`. Envie a `X-Chave-Sistema` apenas entre servidores, sem `Origin`. O JavaScript em outra origem não consegue ler `Retry-After`. Use os intervalos da matriz para 409 e 503 e espera crescente para 429.

## Painel do operador

Já estão disponíveis, adiantados da etapa 3, o login por `POST operadores/sessoes`, a consulta por CNPJ em `POST operadores/clientes/consulta` e a saída em `DELETE operadores/sessao`. O operador entra com usuário do G360 e precisa ter acesso à empresa da loja. A consulta exige o acesso `00500`. Use a sessão própria do operador, separada da do comprador. Nenhuma chave fixa fica no código do painel.

### Galeria de fotos

Use `operadores/produtos/{id}/fotos` com a sessão do operador. `GET` lista as fotos e a capa. `GET .../fotos/{item}` devolve os bytes da foto com a mesma sessão, inclusive para produto fora do catálogo. Para mostrar a imagem em outra origem, faça a requisição autenticada e use os bytes como imagem.

`POST` vincula um JPEG por vez. Envie `foto` como data URL `data:image/jpeg;base64,…` e, opcionalmente, `descricao` de até 50 caracteres. `DELETE .../fotos/{item}` desvincula. `PUT .../fotos/capa` recebe `{"item": 2}`. `PUT .../fotos/ordem` recebe todos os itens visíveis sem repetição, por exemplo `{"itens": [2, 1]}`. A capa explícita continua na primeira posição. Quando ela é removida, a próxima foto na ordem vira a capa.

Para listar e abrir fotos vale 01100, 01101 ou 01102. Incluir e remover exigem 01101 ou 01102. Definir a capa e a ordem exige 01101. A API aceita até 12 fotos por produto. Se a base já tiver mais anexos de imagem, a listagem devolve os 12 primeiros e novas inclusões são recusadas enquanto não houver vaga. Uma referência de anexo cujo arquivo está indisponível pode retornar 404 na leitura. Antes de repetir um POST que perdeu a resposta, consulte a galeria.

### Preço, custo e margem

`POST operadores/produtos/busca` aceita os filtros de `POST produtos/busca` e inclui produtos que ainda não foram publicados. Use 01100. A busca geral consulta a tabela padrão do G360 e pode mostrar preço mesmo sem saldo.

`POST operadores/produtos/precos` recebe o código do cliente, por exemplo `{"cliente":42,"ids":[101,102]}`. Aceita de 1 a 50 IDs e devolve os produtos encontrados na ordem do pedido. Exige 01100 e 00500, com o recorte de empresa e vendedor do operador. Nessa consulta, o preço segue a tabela, a natureza e a política de estoque do catálogo do comprador. `origem_preco` informa `tabela`, `formula` ou `cadastro` quando há preço.

Sem 01110, `custo_visivel` é falso e `custo` e `margem_percentual` são nulos. Com 01110, a margem é o percentual sobre o preço de venda. Se faltar a linha de custo, custo e margem são nulos. Se faltar preço, a margem é nula.

### Preço congelado

No painel do operador, um preço aceito na negociação só passa a valer depois que o operador com o acesso 500110 o grava. A negociação é individual por cliente, produto avulso e unidade. Informe valor e datas inicial e final. Os dois dias contam e a API recusa períodos sobrepostos para a mesma combinação.

Use `GET` para listar e `POST` para incluir em `operadores/clientes/{cliente}/precos-congelados`. Use `PUT` para mudar valor e datas e `DELETE` para encerrar em `operadores/clientes/{cliente}/precos-congelados/{preco}`. A alteração fica no histórico do G360. Na lista, `disponivel: false` indica que a base precisa ser atualizada e `proximo` fornece o cursor `apos` para a página seguinte.

Mostre “Seu preço” quando `seu_preco` tiver valor. Enquanto a condição estiver vigente, a API aplica o menor valor entre o combinado e o da tabela aplicável à quantidade e unidade. Se houver apenas o preço negociado, aplica esse valor. Depois da vigência, catálogo e revisão voltam a mostrar a tabela. No pedido confirmado, o campo conserva o preço da compra. Kits seguem o preço dos componentes.

## Homologação e suporte

A Movimento informa a URL-base e os usuários de teste por canais combinados, com senhas e chave em canal separado. A base de homologação é uma cópia da base de vocês, atualizada no começo de cada etapa. Um link emitido nesse ambiente devolve o e-mail de teste configurado para a loja. A função deve usar exatamente esse destinatário para evitar envio a compradores reais.

Ao pedir ajuda com a API, conforme o item 36 do escopo, informe o que aconteceu, a operação, o horário e o `request_id`. Envie somente dados que ajudem a localizar o caso, sem credenciais ou informações pessoais.
